prefixprobe

If a lab can afford only a slice of Multi-step SWE for a new model, which slices should it run, and how well do they predict the model's full step rate and solve rate? Each of the benchmark's nine published models is held out in turn and predicted from a budgeted set of task prefixes.

The idea

Pay for prefixes, because steps depend on each other

Multi-step SWE chains 5 to 15 dependent engineering requests on one codebase. Step k can only run after steps 1 to k−1, so the natural unit to buy is a prefix of a task. The planner spends a fixed budget on prefixes, best gain per unit of cost first. An estimator then fits two ability offsets for the new model and extrapolates to the steps it did not run.

One example: the strongest model's true step rate is 56.8%. With no probe the estimate is 23.83 points low. With the greedy probe at 10% it is 3.49 points low.

This is an independent analysis of Klavis AI's published results. It is not affiliated with Klavis AI and says nothing about their own process.

Limits

What this does not show

  • Nine models means nine held-out folds. The bootstrap resamples tasks, not models, and a future model generation may rank steps differently.
  • The cost unit is recorded agent time from the other models, not dollars. A new model's own speed is unknown.
  • The planner is fixed in advance, not adaptive, and its design was checked on the same nine models it is evaluated on.
  • The estimator is deliberately simple. It is a baseline, not a claim about the best possible method.

Technical details

Method, results and data terms

The estimator

  • A step's difficulty is the log-odds that the other models pass it.
  • The new model gets two separately fitted ability offsets: one for passing a step, and one for passing it after a clean prefix, which drives the solve rate. Each is fitted by MAP under a normal prior.
  • For unprobed steps only their run counts are used. Run counts are fixed before probing, so they weight the extrapolation, and no unprobed outcome enters it.

This is textbook item-response theory, not a new statistical method. What is specific here is the planning problem: items arrive in dependent chains, each has its own cost, and the bill for a chain is the sum of its prefix.

Solve rate

There is no solve-rate gain over the simple baselines. Greedy's solve-rate error is higher than cheapest_tasks' at every budget, and its difference from random includes zero at every budget. Its only solve-rate intervals that exclude zero are against none at 10%, 20% and 30%, and against uniform at 10%, where uniform spends nothing.

Data and cost

The benchmark's published results cover 69 tasks, 574 steps and nine models with four runs per task. Runs continue after a failed step, so a run's first k scores are exactly what a probe of the first k steps would produce. The cost of a prefix is the mean recorded agent time per run of each step, summed over the prefix.

Data terms. The site states no license for this data, so the repository does not include it. It holds the code, a fetch tool, a sha256 manifest and the derived aggregate results only. Anyone reproducing the experiment fetches the data themselves, and .gitignore keeps it out of commits. CI never downloads it, and the three data tests skip there.

Reproduce

python3 -m venv .venv && . .venv/bin/activate
pip install numpy==2.5.4 scipy==1.18.1 ruff
python tools/fetch_data.py     # fetches and checks the published results
make test                      # 80 tests
make lint
python experiment.py --out results/metrics.json   # about 7 minutes
python demo.py --readme README.md --out README.md

Two runs of the same command produce byte-identical results, so a rerun is checkable with git diff.
